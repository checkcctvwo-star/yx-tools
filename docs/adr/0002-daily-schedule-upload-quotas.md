# 每天固定时刻、分地区配额与固定附带列表

v3.2 把定时任务与上报机制各扩展了一层：定时任务在「间隔模式」之外支持「每天固定时刻」
（24 小时制、一天多个时间点）；上传从全局「优中选优取前 N」扩展出分地区配额与固定附带
列表；下载阶段增加「全部测完再挑」策略；同时修复了测速完成后前端按钮卡死的问题。

## 每天固定时刻

需求：用户要在 24 小时制下键盘输入具体时刻（如 `08:30`、`20:15`）作为定时执行时间。

- `ScheduleTask.Mode`：`"daily"` 表示每天固定时刻，其余值/缺省为间隔模式（老配置兼容）。
- `ScheduleTask.Times`：`HH:MM` 列表，一天可多个；非法项过滤、统一格式化为两位、去重。
- 调度器 `nextRun()`：interval 直接推一个周期；daily 取今天/明天所有时刻里最早且严格
  晚于 now 的那个，按服务器本地时钟（`time.Local`）计算。任务每次跑完/跳过都重新计算
  NextRun，天然支持跨天回绕。
- 时区决策：不做时区选择器，容器本地时间即执行时钟；表单显示「服务器当前时间」提示，
  NAS 用户通过 `TZ` 环境变量设时区（镜像已内置 tzdata）。

## 分地区配额

需求：上传时按地区指定数量（吉隆坡/新加坡/香港/日本/台北可点击选择，也支持手动机场码），
某地区凑不够时可选策略。

- `RegionQuota{Name, Colos, Count}`：一个地区可对应多个机场码（日本 = NRT+KIX+ITM+FUK），
  手动输入机场码自动生成行；「其他地区」数量兜底配额地区之外的结果。
- 装配函数 `BuildUploadList(rs, UploadPlan)`：纯函数、可单测。配额为空走旧 TopN/Limit
  逻辑；否则按声明顺序先取各地区自己的结果，不足时按 `QuotaFill` 少传或用剩余结果补位，
  最后处理「其他地区」；全程按速度降序稳定取用，结果同 IP 只进一个配额行。
- 配置作用域：全局配额（上报配置弹窗）作用于手动上传与命令行；定时任务保存时快照一份
  （沿用 TopN 的既有快照语义），改全局不影响已建任务。
- 与 TopN 的关系：配了配额就以配额总量为准，「上报数量」输入框不再生效。

## 固定附带列表

需求：每次手动/定时上传都必定附带某些指定的 IP 或域名，每条可以命名。

- `FixedItem{Addr, Name}`：全局配置，所有上传路径生效（手动 GitHub/Worker、定时、
  命令行 `yx upload`）。
- 语义：不参与测速；上传时解析为 `Result{Fixed:true}` 附加在末尾；与测速结果同 IP 去重
  （保留固定条目）；GitHub 写 `IP:port#名字`（域名默认端口 443），Worker 用名字字段；
  Worker「清空再上报」时随本次重新写入。

## 下载策略

需求：1900 个候选在测速中途凑够数量就停（现状），用户希望可选「全部测完」。

- `Options.DownloadAll` → 内核 `task.DownloadAll`。
- `downloadQueue()` 纯函数：全部测完 = 候选有多少测多少；否则维持现状（设了速度下限
  或候选不足就全测，否则只测前 N）。
- 提前 break 条件改为 `len(speedSet)==TestCount && !DownloadAll`。
- 默认仍是「测够了就停」，与历史行为一致。

## 按钮卡死修复

现象：测速完成后左下角按钮保持红色「停止」，点击无反应，只能重启容器。

根因：SSE 断线重连后，`Subscribe()` 从最旧的历史事件开始回放，通道容量 64、历史上限 200，
末尾的「完成」终态事件被挤掉；被回放的最旧进度事件又让前端重新进入「测速中」状态。
前端从不主动核对后端状态，于是永久卡死。

修复三件套：

- `Subscribe()` 只回放最新 ≤64 条，终态事件必达；
- 前端每 5 秒轮询 `/api/status` 校准开始/停止按钮，SSE 断线重连与点击停止后各补一次校准；
- 完成后按钮立即复位，可马上再点下一轮。

## Considered Options

- **每天固定时刻 vs 只改频率单位**：频率本质是「相对时间」，固定时刻是「绝对时间」；
  两者语义不同，并存（每条任务二选一）而非替换，老任务不受影响。
- **时区选择器 vs 服务器本地时钟**：一台 NAS 一个时区，`TZ` 环境变量一次到位；
  选择器要引入时区库与夏令时换算，收益低，不做。
- **配额与 TopN 叠加 vs 二选一**：叠加会让用户搞不清最终数量，二选一语义清晰。
- **固定条目参与测速 vs 不参与**：域名无法用测速内核测试，信任条目原样附带更符合
  「必定上传」的语义。
- **SSE 保底 vs 仅前端轮询**：只修服务端回放仍有丢事件的可能（慢客户端、广播溢出），
  只修前端则服务端状态不可靠时兜不住；两者都做，互为冗余。

## Consequences

- 定时任务的时间表达多了一种模式，`NextRun` 计算统一收敛到 `nextRun()`，调度 tick 仍是 30 秒。
- 上传流程多了一层装配（`BuildUploadList`），`UploadToAPI/UploadToGitHub` 签名不变，
  调用方（手动、定时、CLI）统一先装配再上传。
- 固定条目在 Worker 列表与 GitHub 文件里都以「用户名字」出现，与测速结果的
  「地区-速度」格式区分。
- 前端状态与后端在 5 秒内必然收敛，测速中/停止/完成不再依赖 SSE 事件完整性。
